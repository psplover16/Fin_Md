### 一、 資料庫交易 (Transaction) 基礎概念
*   **交易的定義**：交易是資料庫中一個不可分割的工作單位，由一連串操作組成。其核心精神為「全部成功」或「全部失敗」。
*   **資料更新的底層流程**：
    1. 發送 UPDATE 命令與「搜尋核對」。
    2. 在記憶體中修改資料。
    3. 發送 COMMIT 命令給資料庫，宣告交易準備結束。
    4. 寫入交易記錄檔（Transaction Log），該步驟完成的這一瞬間，交易結束。
    5. 背景非同步寫回硬碟。
*   **ACID 四大特性**：
    *   資料庫必須符合 ACID 特性。
    *   **原子性 (Atomicity)**：交易中所有操作「全部完成」或「全部不做」；失敗時以 ROLLBACK 復原。
    *   **一致性 (Consistency)**：交易執行前後，資料庫都維持在符合所有完整性限制的合法狀態，此為終極目標。
    *   **隔離性 (Isolation)**：多個交易並行時互不干擾，一交易的中間結果不被其他交易看見。此特性以鎖定（Locking）或 MVCC 達成。隔離性負責處理「時間順序與併發排隊」，把「同時發生」的混亂交易，強制排成一條有秩序的單行道。
    *   **持久性 (Durability)**：交易一旦 COMMIT，變更即永久保存，即使系統故障也不遺失；以交易記錄檔（log）達成。交易記錄檔用來記錄所有已提交（COMMIT）但尚未寫入資料檔的變更，以確保系統崩潰時能還原資料（由 SQL 內部自行處理）。
    *   **核心公式**：原子性 (A) + 隔離性 (I) + 持久性 (D) = 一致性 (C)。

### 二、 隔離性 (Isolation) 與讀取異常
*   **隔離性的挑戰**：隔離性是最難維護的特性，容易產生併發異常。隔離性是確保多筆並發交易互不干擾，使其宛如獨立執行以維持資料一致性的核心機制。
*   **三種讀取異常**（難以預防的程度：幻讀 > 不可重複讀 > 髒讀）：
    *   **髒讀（Dirty Read）**：讀到另一交易尚未提交的資料。
    *   **不可重複讀（Non-repeatable Read）**：在同一交易內前後讀取同一筆資料，卻因其他交易在期間內完成「更新 (Update) 或刪除 (Delete)」，導致兩次讀取的數值或狀態不一致。
    *   **幻讀（Phantom Read）**：在同一交易內前後執行相同的範圍查詢，卻因其他交易在期間內「新增 (Insert)」或「刪除 (Delete)」了符合條件的紀錄，導致第二次查詢得到的資料與之前不相同。幻讀僅靠序列化才能防禦。
*   **隔離等級 (Isolation Levels)**：
    *   隔離等級是資料庫提供的設定規範，讓開發者根據業務需求，在「資料嚴謹度」與「系統併發效能」之間進行權衡與取捨。探討的是「系統整體的狀態」。
    *   隔離等級幾乎都是為了決定 SELECT 該如何表現而設計的，至於 WRITE，所有等級的防護底線都一樣嚴格。
    *   **Read Uncommitted**：讀未提交，完全無防禦力。
    *   **Read Committed (RC)**：讀已提交。
    *   **Repeatable Read (RR)**：可重複讀，確保交易內針對同一筆紀錄的多次讀取結果恆定 (MYSQL 預設)。
    *   **Serializable**：序列化 / 串行化，最高隔離層級，強制所有並發交易必須循序排隊執行。最嚴格、效能極差，但能防止全部讀取異常。

### 三、 併發控制機制 (Concurrency Control)
*   **機制目的**：為了確保隔離性，資料庫採用了併發控制機制，用來控制「當多個交易同時發生時，該怎麼調度」。
*   **MVCC (Multi-Version Concurrency Control, 多版本併發控制)**：
    *   **定義**：當資料被修改時，資料庫不會直接覆蓋過去，而是會保留歷史版本（透過 Undo Log 串成版本鏈）。這是一種透過「保留資料歷史版本快照」來達成「讀寫互不阻塞」的底層機制。
    *   **特性**：「用空間換時間」。讀寫不互斥，讀的人去讀歷史快照（快照讀），寫的人去改最新版，雙方互不干擾，大幅提升併發效能。它讓讀取操作不需要等待寫入鎖定（如果不加 FOR UPDATE 會自動套用，由 SQL 內部自行處理）。
    *   **【進階補充：MVCC 在 RR 與 RC 的決定性差異】**
        *   **RC 等級：** 每次執行 SELECT，都會產生一個「全新的快照」，所以別的交易剛 COMMIT，你立刻會讀到最新變更（無法防禦不可重複讀）。
        *   **RR 等級：** 只有在交易內的「第一次 SELECT」會產生快照，之後的 SELECT 都「沿用同一個舊快照」，因此不管別人怎麼改，你看到的都跟第一次一樣，達成可重複讀。
*   **Locking (鎖定機制 / 悲觀鎖)**：
    *   **定義**：透過對資料加鎖限制多個交易同時存取同一資源。資料庫控制多個使用者同時存取的基礎防護機制總稱。
    *   **特性**：「用排隊換正確性」。這是一種「先上鎖再做事」的策略，假設衝突一定發生，讀取時立刻獨佔資源（如 FOR UPDATE），適用於高衝突場景。缺點是排隊效率差。
*   **樂觀鎖 (Optimistic Locking)**：
    *   **定義**：其實不是鎖，屬於「不鎖門，做事後才檢查」的策略。
    *   **特性**：假設衝突很少發生，直到更新（UPDATE）時才核對資料有沒有被別人改過，適用於低衝突場景。
    *   **缺點**：因為是最後一步才檢查，海量資料下，伺服器會一瞬間收到大量失敗的 UPDATE，導致使用者體驗不好。

### 四、 鎖定機制與行為詳解 (悲觀鎖)
*   **鎖的類型**：
    *   **S-Lock (Shared Lock, 共享鎖)**：核心精神就是「唯讀不寫」。
    *   **X-Lock (Exclusive Lock, 排他鎖)**：拿到 X-Lock 的那「唯一一個人」，擁有絕對的獨佔權與修改權。
    *   S-Lock 與 X-Lock 兩者都是悲觀鎖的工具。探討開發者如何手動控制併發，屬於悲觀鎖的範疇。
*   **鎖的運作規則**：
    *   鎖的唯一目的，就是用來「防禦外部交易 (其他併發的請求)」來干擾你現在這筆交易，所以在同一筆交易內，可以進行 CRUD。
    *   SELECT 預設不加鎖；UPDATE、DELETE 預設自動加鎖。
    *   SELECT 撈到的資料是陣列。
    *   FOR UPDATE 是「當前讀 (Current Read)」，FOR SHARE 也是。
    *   FOR UPDATE / FOR SHARE 的範圍是「掃描過的行，通通都要上鎖」（所以如果有建索引，會少很多鎖定範圍）。
*   **交易間的鎖相容與升級機制**：
    *   A 交易先 FOR UPDATE，B 交易執行普通 SELECT 是可以的，但其他 FOR UPDATE、FOR SHARE、UPDATE、DELETE 會被禁止。
    *   同一筆交易，FOR UPDATE 先，可以兼容 FOR UPDATE，也可以做其他等級的 SELECT。
    *   同一筆交易，先 FOR SHARE，若使用 UPDATE，則鎖會升級（鎖只會升級）。
    *   **【實務踩坑點：死結 Deadlock】** 盡量避免先 SHARE 再 UPDATE。若交易 A 與 B 同時對同一筆資料下 FOR SHARE (皆取得 S-Lock)，隨後雙方都要求 UPDATE (要求升級為 X-Lock)，雙方會互相等待對方釋放 S-Lock，直接引發死結。若確定要改，建議一開始就直接 FOR UPDATE。
*   **Gap Lock (間隙鎖) 與 Next-Key Lock 的觸發條件**：
    *   **【進階補充：鎖的完全體 Next-Key Lock】** MySQL (InnoDB) 在 RR 等級下，預設使用的其實是 Next-Key Lock (行鎖 + Gap Lock 的結合體)。它不僅鎖住紀錄，還會把紀錄前後的空隙鎖起來，用來防止幻讀。
    *   如果 A 的 FOR UPDATE 是範圍查詢 (如 `WHERE id BETWEEN 1 && 10 FOR UPDATE`) 或沒打中唯一索引，若 B 交易要新增，需看以下隔離等級：
        *   **RC 等級** ➔ 沒這煩惱，沒有 Gap Lock。
        *   **RR 等級 + 唯一索引精準查到現有資料** ➔ 只有行鎖，沒有 Gap Lock。
        *   **RR 等級 + 範圍查詢 / 模糊查詢 / 查不到資料** ➔ 一定有 Gap Lock，空隙被封鎖。
    *   **【實務踩坑點：非唯一索引的陷阱】** 即使 WHERE 條件是精準打中資料（如 `WHERE age = 18`），只要該欄位是「普通索引（非唯一）」，為了防止別人再塞一筆 18 歲的資料，資料庫依然會觸發 Gap Lock 鎖住空隙。
*   **二階段鎖定協定 (Two-Phase Locking Protocol, 2PL)**：
    *   為了讓這些鎖（S-Lock / X-Lock）完美運作、不出錯，交易必須嚴格遵守 2PL (二階段鎖定協議)。這保證了有衝突的交易在更新資料時仍保持資料的正確性。
    *   **【2PL 運作原理解析】** 2PL 規定交易在運作時，鎖的操作必須分為兩個階段，且絕對不能交錯：
        1.  **擴張階段 (Growing Phase)**：交易只能不斷「獲取鎖」，絕對不能釋放任何鎖。
        2.  **收縮階段 (Shrinking Phase)**：一旦交易釋放了「第一個鎖」，就進入收縮階段，此後只能「釋放鎖」，絕對不能再要求獲取新鎖。
    *   只要嚴格遵守 2PL，數學上可證明絕對能避免資料不一致的衝突（保證可串行化），但代價是可能增加死結發生率或降低併發效能。

### 五、 實戰演練與程式碼範例 (教學文件)

#### 1. 交易控制指令 (TCL) 範例
```sql
-- 🚪 開啟交易防護罩
START TRANSACTION;
UPDATE users SET balance = balance - 10000 WHERE id = 1;

-- 💾 ★ 設立存檔點 (SAVEPOINT)，在此之前的狀態、記錄存起來
SAVEPOINT point_flight;

INSERT INTO orders (user_id, item, status) VALUES (1, '機票', '成功');

-- ⏪ ★ 回復到指定存檔點 (部分 ROLLBACK)
ROLLBACK TO SAVEPOINT point_flight;

-- ROLLBACK，把全部的操作徹底撤銷 (ROLLBACK對應 交易的原子性：全有或全無)
ROLLBACK;

-- ✅ ★ 永久寫入 (COMMIT，對應持久性)
COMMIT;
```

#### 2. 基礎交易與 FOR UPDATE 應用
```sql
START TRANSACTION;
-- 先 SELECT FOR UPDATE 找到資料 ['a','b']
-- 再 INSERT 'c'
-- 
COMMIT;
```

#### 3. 變數使用方式與作用域陷阱
```sql
-- 【方式一】使用 @ 變數
-- 相當於 JS 的: let a = (SELECT SUM(amount) FROM expenses);
SELECT SUM(amount) INTO @a FROM expenses;

-- 把變數拿出來看，或是做後續運算
SELECT @a; 
SELECT @a * 1.05; -- 例如加上 5% 稅金
-- ⚠️【實務踩坑點】：@ 變數是「用戶端連線變數 (Session Variable)」，隨時隨地都可以宣告與寫入。

---------------------------------------------------
-- 【方式二】使用 DECLARE
DECLARE a INT;  -- 先宣告一個整數變數 a (類似 let a;)
SELECT SUM(amount) INTO a FROM expenses; -- 把結果塞進去
-- ⚠️【實務踩坑點】：DECLARE 是「區域變數 (Local Variable)」，它只能寫在 Stored Procedure 或 Function 的 BEGIN ... END 區塊裡面。直接在查詢視窗單獨執行 DECLARE 會報錯！
```

#### 4. 悲觀鎖 vs 樂觀鎖實戰範例 (提款情境)
假設有一張 `accounts`（帳戶）資料表。你要提款 500 元，目前資料庫裡的狀態是：`id = 1`（你的帳戶），`balance = 1000`（餘額 1000 元），`version = 1`（資料版本號，給樂觀鎖用的預設值）。

**悲觀鎖實作**：
```sql
-- 1. 開啟交易防護罩
START TRANSACTION;

-- 2. 查詢餘額，並【強制上鎖】 (此時別人完全不能動這筆資料，只能排隊乾等)
SELECT balance 
FROM accounts 
WHERE id = 1 
FOR UPDATE;

---------------------------------------------------
-- [後端程式邏輯]
-- 程式拿到 balance = 1000
-- 判斷 1000 >= 500 (餘額充足，允許提款)
---------------------------------------------------

-- 3. 執行扣款
UPDATE accounts 
SET balance = balance - 500 
WHERE id = 1;

-- 4. 提交交易，並【自動解鎖】
COMMIT;
```

**樂觀鎖實作**：
```sql
-- 1. 查詢餘額與【當前版本號】 (一般 SELECT，不加鎖，大家都可以同時查)
SELECT balance, version 
FROM accounts 
WHERE id = 1;

---------------------------------------------------
-- [後端程式邏輯]
-- 程式拿到 balance = 1000, version = 1
-- 判斷 1000 >= 500 (餘額充足，準備提款)
---------------------------------------------------

-- 2. 執行扣款，但把剛剛拿到的 version = 1 當作【核對條件】
-- 同時將 version 升級 (+1)
UPDATE accounts 
SET balance = balance - 500,
    version = version + 1
WHERE id = 1 
  AND version = 1;  -- 👈 關鍵防線：必須還是第 1 版，我才要更新！

---------------------------------------------------
-- [後端程式邏輯 - 驗證結果]
-- 資料庫會回傳「影響了幾筆資料 (Affected rows)」：
-- 
-- 狀況 A：回傳 1 筆 -> 代表沒人動過，提款成功！(自動 COMMIT)
-- 狀況 B：回傳 0 筆 -> 代表在你操作的瞬間，別人已經改過這筆資料 (version 已經不是 1 了)。
--                   這時後端程式就要拋出錯誤訊息給使用者：「資料已變更，請重新整理」。
---------------------------------------------------
```
